# clash-home 手机订阅缓存：变更触发 + 原有定时兜底（设计方案）

> 2026-11-21 方案设计。**SOURCE_ONLY / NOT_DEPLOYED**。不得把本文件视为设备已修改或ClashMate故障已修好。用户明确不采用“单次手动刷新”作为长期修复。

## 用户原目标及不可改边界

- Android ClashMate 始终使用 `http://10.68.10.2:18080`，`clash-home` 的 `cache/merged.yaml` 提供**事先生成**的订阅内容，不因手机打开订阅而实时调用耗时/可能超时的 subconverter。
- 上游**有效订阅内容**或转换模板、转换器版本发生变化 → 后台自动更新缓存；没有发生变化 → **保留原每日04:30主动刷新**（不是停掉定时任务，也不是纯凭mtime重复读取旧缓存）。
- 后台刷新故障必须保留上一份可用完整缓存、入口继续可读，不重复爆发转换请求。保留正常手机规则和现有AI、Telegram、游戏分流；不改手机URL、不增加新Docker、不重启OpenClash/25500。
- 当前缺陷已证：2026-11-21 18:52 实机 `18080` 与 `cache/merged.yaml` **逐字节一致**，文件mtime 14:50:26早于新版subconverter于16:27完成切换；其54个AnyTLS全部缺SNI，美国A01 5/5缺SNI。单纯手机刷新18080不可能消除此缺陷。
- 2026-11-21 18:58 匿名审计显示旧 `refresh-current.sh` 调用现存 `refresh.py`，`refresh.py` 代码有“临时文件/写入/缓存替换/异常”相关标签，`watch-clash-li.sh` 有监测、锁、刷新标签；**只能证明有相关逻辑，不等于已审核真实实现、锁竞态或HTTP源的位置**。

## 推荐的单套刷新机制（共用一个worker、两个触发入口）

```text
已知现有上游输入 ──[轻量变化检测，复用已有watch/事件]──┐
                                                      ├──> 单个后台刷新 worker
每日04:30定时刷新 ──────────────────────────────────────┘    │
                                                          ├─取正式25500转换结果
                                                          ├─merge.py 合并手机专用配置
                                                          ├─对临时YAML做安全门禁
                                                          ├─与现有缓存比对，必要时原子发布
                                                          └─成功提交输入指纹 + 操作结果

ClashMate ──HTTP GET 18080──> 只读上一份已发布 merged.yaml
```

### 触发语义

1. **变更触发**：优先使用已经存在的 `watch-clash-li.sh` 检测机制，不能为此另启一套重复的五分钟常驻任务；确认现行watch的真实监控路径后扩展到 **实际影响手机转换产物的输入**：
   - 机场原始订阅（如有本地可信快照/安全的源版本标识）；
   - `Clash-Li.ini` 转换规则、手机专用叠加配置；
   - 正在使用的 subconverter **实际运行镜像ID**（2026-11-21实际更新镜像是本次最重要的漏检维度）；
   - 影响最终输出的 `refresh.py`、`merge.py` 等发布版本。
   输入变更检测以内容指纹/可靠版本标识为依据，不把mtime或`cache/merged.yaml`自身变化当作订阅源变更，以免形成自触发循环。
2. **源为动态HTTP且无便宜的版本信息时**：绝不每5分钟调用完整25500转换或下载整份订阅以“检查是否变化”，这正是用户以前超时的来源。优先复用原始订阅现有的本地落盘成功更新事件或已有可靠 ETag/Last-Modified；这些若当前不存在，则保持每日04:30主动拉取的兜底语义，记录“无法实时检测远端源变更”的真实边界，不伪称能即时感知。
3. **定时触发**：原有04:30刷新入口与变更触发共享**同一个**实际刷新worker。即使输入指纹没变，04:30仍对上游做一次正常转换与结果比对；若结果逐字节一致，不改写`merged.yaml`，仅记录本次任务成功。
4. **失败与去重**：所有触发共用跨进程排他锁（复用现有锁后确认锁语义；不得新旧刷新并行）。变更事件合并/短时防抖；正在刷新则合并成一次待处理；失败后保持上次成功输入指纹不变，限流重试且每日04:30兜底继续有效。绝不将失败标记为“已更新”。
5. **生成/校验/发布**：只在私有同文件系统临时路径下载/合并、完成解析后校验AnyTLS字段（尤其A01 SNI）、节点数量异常大幅下跌、策略组缺失、文件非空与权限；成功才使用同文件系统rename/replace原子发布。保存上一份已发布正常缓存备份（权限、属主一致），异常不覆盖；HTTP服务继续读取旧缓存。刷新日志不得泄露URL/token/节点密码。
6. **恢复既有SNI缺陷**：由于旧缓存早于已修复converter上线，**实际converter镜像ID变化必须触发一次后台刷新**（不能仅在节点数量/订阅URL变化时刷新）。但此前25500的SNI只验证过合成AnyTLS，实际机场订阅仍需通过新缓存SNI门禁和手机A01真实连接证明。

## 精确验收项目

| 验收情形 | 预期 |
|---|---|
| 手机打开/更新 `18080` | 仅取当前已发布缓存，不发起同步转换，快速响应 |
| 有新原始订阅/转换模板/25500镜像变更 | 单个后台任务生成新缓存，经校验后一次性发布；手机下一次更新获取新结果 |
| 上游无变化 | 原04:30照常检查更新；相同产物不重复覆盖 |
| 5分钟监测与04:30同时发生 | 只允许一次刷新执行，另一触发合并或跳过，不破坏cache |
| 源超时、转换失败、生成内容缺SNI、YAML损坏或节点异常缺失 | 不发布新内容，不清理旧cache，保存HOLD原因 |
| 当前生产A01问题 | 18080新输出A01 AnyTLS全部有非空有效sni，其他原有策略组完整，手机ClashMate节点真实连接成功 |
| 并发/断电 | 同盘原子发布前旧cache始终有效；重启后能识别上次完成状态，避免把未发布指纹视为成功 |
