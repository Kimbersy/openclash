# 三端共享订阅转换：AI 动态增强隔离契约（2026-11-13，候选方案，未部署）

> 用户最新确认：**家中 iStoreOS/OpenClash、安卓 Clash Mate、苹果 iPhone/iPad Shadowrocket 均使用同一套订阅转换**。这覆盖之前对“手机订阅独立”的假设。用户要求：如果 AI 智能监测/防抖只可在路由器实现，就必须**从设计开始防止对安卓、苹果端造成规则、订阅更新、策略选择上的影响**。

## 绝对验收要求

1. **一个源，不等于所有终端必须使用同一份完全相同的最终配置。** 保持现有共享订阅转换的入口、账号/Token/KV、域名规则和正常输出；区分路由器本地后处理与 Android / iOS 各自的兼容输出。不要未经确认给三端更换订阅链接，也不要把路由器生成的设备专属 YAML 直接推给 Shadowrocket。
2. **既有公共转换的发布基线冻结直到三端验证：** `main/Clash-Li.ini`、`main/list/AI.list`、`main/generated/Clash-Meta-Android.template.yaml` 暂不随这项动态 AI 功能修改。即使 GitHub 上的候选 PR 改了文件，也不能默认与公共 `main` 合并。当前 `Clash-Li.ini` 中 `ruleset=🤖 AI` 及 `custom_proxy_group=🤖 AI` 维持原分流语义；国内/流媒体/Disney/工作等原有策略不受影响。
3. **仅路由器本地使用动态控制器：** iStoreOS OpenClash 与 Mihomo 的订阅成功生效事件、私有节点指纹、健康缓存、国家/平台业务资格、故障防抖及有限 API 调整，只能存在于本机路由器私有层；不写入共享的 `Clash-Li.ini` / `AI.list` / Android YAML，不在 Cloudflare Worker/KV 生成给所有设备的输出中夹带控制服务信息、外部控制器 token、路由器内部地址、地区缓存/健康结果。
4. **客户端能力分层：** Android Clash Mate 可以继续使用它当前能够导入的订阅转换格式/原有策略组，但路由器的周期检测和自动切换逻辑**不会因共享订阅而自动在 Android 上运行**；Shadowrocket 保持现有专用解析/导入结果与手动选择，不能假定它支持全部 Mihomo 的特定 `proxy-groups`、`proxy-providers` 或控制 API。若将来要手机端也具备相同能力，应开发**独立适配器或客户端支持的本地智能策略**并逐端验收，而不是混合源代码或要求安装路由器守护进程。
5. **订阅动态变化相互隔离：** 同一机场每日更新，三端可以各自按现有日程获取更新，但路由器自动识别当前活动节点、维护 AI 资格数据库，不应向公共订阅 URL/KV 写入节点重命名或自动选择结果；不因路由器切线修改移动设备的节点列表、当前手工选择、证书、DNS、规则组或订阅更新频率。
6. **Wi-Fi 拓扑特别验收：** 手机通过家中旁路由出网可能产生网络层两套代理/分流交互。这需要实机检查 Wi-Fi DNS/网关/Shadowrocket TUN 工作路径，不能仅凭“脚本只在路由器运行”保证手机在家庭 Wi-Fi 绝无间接影响。外出移动网络的 Shadowrocket/Clash Mate 不应由家中路由器 API 控制。

## 已经核对的真实源码

- [公开 Android 生成模板](../generated/Clash-Meta-Android.template.yaml)：文件声明 `Source: Clash-Li.ini`，其 `proxy-providers.Airport` 订阅URL为 `__AIRPORT_URL__` 占位符，保留 `🤖 AI` 等公共策略组。
- 私有 `Kimbersy/clash-config-worker` 已核对生产源码：`/config?token=...` 从原本 `USERS` KV 取机场URL并下载上述**公共 main Android 模板**填入 URL；已有活动版本及字节级一致性回执，不应因 OpenClash 项目擅自改动该 Worker 或 Token/KV。**此证据证明 Worker 模板路径，不等于确认苹果端 Shadowrocket 所消费的实际最终格式**；用户已经确认三端使用同一套订阅转换，但每端转换输出与设备上的真实订阅地址还需在正式发布前只读核验，且不得索取明文 token。
- 2026-11-13 发现候选分支之前曾在共享 `list/AI.list` 添加 `DOMAIN,notebook.google`（NotebookLM 新介绍页）。该修改**已在候选分支撤销以还原 main 基线**；如需为路由器补足跳转链，只能在未来安全验证的**路由器本地规则覆盖层**实现，不能借 AI 动态工程顺手向移动客户端公共规则推送。

## 目标结构（设计，不代表已部署）

```
                    唯一现有共享转换源（保持不变）
                                  |
                 +----------------+------------------+
                 |                |                  |
         路由器OpenClash      安卓Clash Mate       iOS Shadowrocket
         既有转换结果          既有转换结果         既有转换结果
                 |                |                  |
      （仅路由器本地叠加）       无路由器守护进程      无Mihomo特有控制API
      动态AI资格/国家/切线         原功能保留           原功能保留
```

**实际实施约束**：必须先查明OpenClash的本地后处理/脚本钩子在哪一阶段安全触发、是否被下一次订阅覆盖、怎样回滚，才能生成路由器独享AI组；不能直接假设通过 REST API 可以向已运行Mihomo任意增加新节点/组。路由器候选只允许本地、私有、可逆更改，先DRY_RUN。

## 2026-11-13：用户确认目标是三端共享AI智能，而非路由器永久独享

- **目标澄清**：用户要求三端共同受益于**AI合格节点筛选、按真实国家选择、失败时可靠接替**，并将其类比“自建VPS解决AI访问”。此前“路由器独享动态监控/手机照旧”只应视作**先行灰度/安全隔离措施**，不是最终产品范围。
- **逻辑拆分**：中央调度面（更新/指纹/服务资格/地区/健康/质量与调度建议）与三端数据面、兼容配置适配器独立。三端仍从现有同一订阅转换体系获取原节点与原规则；只有各端能力经过验证，才在其**兼容输出**中启用AI专用合格池。禁止直接给Shadowrocket发送Mihomo动态控制API或假定它能执行同样的稳态状态机。路由器AI分组在本地后处理实现；安卓/苹果先保留当前订阅与手动选择，后续在支持的客户端策略内完成周期刷新/备用自动检测，缺少完全相同控制能力时需明确降级。
- **共享信息不等于共享出口**：调度器观察到的服务可用性/延迟与地区属于**特定节点+时间+测量网络**；跨路由器/安卓/苹果可分享候选资格和节点配置指纹，但客户端在不同网络下仍须本地轻量验证，Google账号的NotebookLM工作区验证不能从无登录HTTP200推定。手机4G/5G与家中固网不应直接继承完全相同的实时延迟/故障结论。
- **VPS角色的三个不同概念**：①不购买VPS也可在已有家用/云托管资源部署中央筛选/发布控制面（服务需安全可达和按需运行）；②VPS只负责中央调度/配置发布时**不会自动统一三端出口IP**；③VPS真正作为固定代理出口可统一对外IP（需分别核实ChatGPT/Gemini/NotebookLM允许该IP，不能保证数据中心IP支持），若VPS只是中转机场，则最终外部IP仍取决于机场出口。VPS可能带来额外成本、运维和单点故障；须先以真实业务结果验证性价比。
- **发布方式**：一份共享源和公共规则基线仍冻结；新AI候选数据要通过兼容目标输出或**经过鉴权的独立配置增量**分发到三端，不能在公共main里直接塞路由器特有API。任何可被公网访问的服务不得暴露机场URL、节点密码、Google凭据、Worker token、路由器API密钥和真实代理出口。
- **交付分阶段**：A. 完成动态状态/资格与订阅更新事件的离线+路由器DRY_RUN；B. 对Clash Mate和Shadowrocket分别验证真实订阅输出格式、兼容策略组、刷新语义/手动锁及外网线路；C. 统一配置发布兼容适配器/端到端功能回执；D. 如果用户要求三端绝对相同稳定出口，则单独比较VPS固定出口并对实际AI业务做长期实测。**目前不存在已上线的中央调度或三端统一切换服务**。
- **新增可验收结果**：①路由器动态增强在不修改共享main转换情况下可用且可关闭；②安卓与苹果均能沿用原订阅并获取已验证合格AI候选组或明确说明该客户端无法原样支持的自动行为；③三端每个实际支持的平台和国家均有更新、手动锁、防抖或降级策略验收；④正式发布失败可独立回滚各端，不破坏国内/Disney/流媒体。
 
## 2026-11-13：AI-only 业务范围硬锁（用户最新明确要求）

- **只调度 AI 规则命中的流量**：ChatGPT、Gemini、NotebookLM及当前`🤖 AI`组确实覆盖的AI服务。对未纳入AI的域名/APP，一律保持原订阅转换处理方式、选择、DNS/网络访问策略。未来如新加AI域名，要逐项检查是否会误命中Google普通产品、GitHub等非AI业务。
- **非AI零行为差异是硬验收**：公共共享订阅转换里的`💻 GitHub`、Telegram、Disney、视频/Netflix、AppleTV、游戏、国内直连及其他原有规则组/自动测延迟/分流次序不得因该工程重排、改名、重写、自动选择或重载副作用而改变。更不能把全局节点最低延迟组统一接管成AI健康组。
- **三端目标**：路由器OpenClash、安卓Clash Mate和苹果Shadowrocket从同一套机场订阅转换继续获得原始非AI行为；只在AI分流处接入AI已验证候选/地区选择/故障接替。中央AI控制面只读识别机场变更与AI服务资格，所有发布数据必须限于AI候选，非AI组不跟随AI切换。各客户端自动故障切换须按客户端原生能力逐端验收，不支持时保持原工作方式，不伪称能力一致。
- **安全部署**：先冻结生产三份公共文件及现有Worker。候选方案优先在路由器本地叠加单独AI组，不修改普通全局流量；手机端AI改进只有跨端实机兼容通过才可选择性推出。任何AI变更造成非AI域名/流媒体/国内或旧手机订阅异常，一票否决并回滚；即使NotebookLM没有实测业务合格候选，也不能迁就把其他用途的策略组改为AI默认。
- **可验证输出**：采集发布前后各客户端生成策略组名/成员、规则组、规则顺序、非AI路由判定/使用时手动选线的差异报告，容许白名单差异只发生在明确登记的AI域名或专用AI策略组；运行测试覆盖路由器固网、Android/Apple家庭WiFi和外部蜂窝网络，同时保持原未改业务的实机回执。
